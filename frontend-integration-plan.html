1. Current State (what's actually there today)

Confirmed by direct inspection, not assumption:

  • No HTTP client at all — package.json has no axios, no fetch wrapper, nothing. Every page reads/writes through React Context, backed by useState initialized from mockData.ts arrays.
  • No data-fetching/cache library — no TanStack Query, SWR, Redux, or Zustand. Plain React state and prop drilling through Context.
  • DataContext.tsx (1,428 lines) exposes ~19 domain state arrays and ~50 synchronous mutator functions. Every one runs instantly and locally — no loading state, no error state, no network round-trip — because there's no network involved yet.
  • AuthContext.tsx has no real authentication: login(email) matches a mock user by email with no password check whatsoever, plus a switchRole() escape hatch that swaps the "current user" to any of the 5 demo personas with one click. Session state is a single localStorage key, not a token.
  • LoginPage.tsx already has a real-looking email/password form, but the password field is decorative — its value is never read or sent anywhere. A "1-click demo personas" panel below logs in as any role instantly, no credentials needed.
  • No route guarding — AppRoutes.tsx renders every role's pages unconditionally; no ProtectedRoute/redirect-to-login mechanism exists.
  • No test tooling — no Vitest/Jest/Testing Library configured. Any testing strategy for this migration starts from zero.
  • No git repository in frontend/ (or anywhere under panther/) at the time of this plan.

None of this is a criticism of the current app — it's a demo/prototype frontend doing exactly what it needs to for that purpose. This section exists so the plan below is grounded in what actually has to change.

2. Target Architecture

  • API client: a small hand-rolled src/api/client.ts wrapping fetch, not a new dependency — the backend exposes a plain REST/JSON API with no need for anything heavier. Base URL from a Vite env var (VITE_API_BASE_URL). Centralizes bearer-token injection, JSON encode/decode, and a single place to handle a 401.
  • Data fetching pattern: the one place worth a new dependency — with ~50 mutations and ~20 reads across 45 pages, hand-rolled loading/error plumbing everywhere would be repetitive and error-prone. Recommended: @tanstack/react-query for caching, de-duplication, refetch-after-mutation, and built-in loading/error states (flagged as an open decision, §8).
  • Auth token storage: access + refresh tokens (JSON body, per the backend's confirmed decision) held in memory plus the refresh token in localStorage, so a page reload doesn't force re-login. The API client transparently retries once after a silent refresh on a 401, redirecting to /login only if the refresh itself fails.
  • Route guarding: a new <ProtectedRoute allowedRoles={[...]}> wrapper around each role's route subtree, redirecting to /login if unauthenticated and to a real "not authorized" state if the role doesn't match — enforcement that doesn't exist today.

4. Data Layer — Domain-by-Domain Rollout

Mirrors the backend's own build order, since each phase there already has a matching, verified REST surface. Each domain phase follows the same inner loop: wire reads → wire writes → smoke-test every page that touched it, across every role that can reach it.

Correction after actually doing the Property domain: deleting a domain's mock arrays out of DataContext.tsx/mockData.ts is not safe to do per-domain, as the original draft of this plan assumed. Dashboards, global search, and several client-portal pages read across domain boundaries (e.g. a dashboard reading properties before the Platform phase that owns dashboards is even wired). The mock arrays for a domain can only be deleted once every consumer across every domain has been migrated — realistically only after the last phase (Platform). Until then DataContext.tsx intentionally serves mock data to not-yet-converted pages alongside the real API serving converted ones — an expected transitional state, not a bug.
