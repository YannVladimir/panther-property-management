4. Why a Flyway Migration (Not an Ad-Hoc Script) — superseded

The backend already uses versioned Flyway migrations (V1__iam.sql … V8__platform.sql) tracked in flyway_schema_history, applied automatically on startup and never re-applied once recorded. That mechanism is the right fit here too: it runs exactly once, is reviewable in version control like every other schema change, and is safe against accidental re-runs that would otherwise create duplicate properties/clients/etc.

Because BCrypt hashing needs to happen once, not per-deploy, the plan precomputes a single BCrypt hash for password@123 and embeds that literal hash in the SQL — standard practice for seed migrations, since the plaintext is already known/documented.

✅ EXECUTED — architecture changed at implementation time. Hand-writing ~200 rows of interlinked SQL across ~40 tables using natural-key subqueries turned out considerably more error-prone than reusing the backend's own JPA entity classes with real, in-memory Java object references. The actual implementation is a Spring ApplicationRunner (LegacySeedRunner) instead of a Flyway SQL file — see Section 5. Same guarantees (runs once, reviewable, safe against re-runs) via a config flag plus a hard skip-if-not-empty check instead of flyway_schema_history. The BCrypt hash was generated with the app's own real BCryptPasswordEncoder bean to guarantee it verifies correctly at login — confirmed live in Section 6.

5. Migration Architecture — as actually implemented

  1. Extraction script: frontend/scripts/extract-legacy-data.ts, run via npx tsx. Imports the real mockData.ts arrays directly (no hand-transcription), applies every fix in Section 3, writes backend/src/main/resources/legacy-seed/legacy-seed-data.json.
  2. Java seeder: LegacySeedRunner implements ApplicationRunner (com.panther.pms.platform), ordered to run after the existing DataSeeder. Reads the JSON via Jackson, inserts via real repositories, maintaining an in-memory legacy-id → saved-entity map per entity type so later inserts resolve real generated ids through actual object references — no subqueries, no natural keys. Order: properties → buildings → rental types (+materials) → rooms (client link deferred) → agents (+deals, since Booking.agent is a hard FK) → clients (+materials) → employees (+documents/tasks/damages) → a backfill pass setting each room's currentClientId now that client ids exist → users (upserted by email) → bookings (+timeline) → payments → expenses → recurring_bills → technicians (+work orders/documents) → preventive_tasks → damage_reports → water_meters (+history) → maintenance_issues → payroll_records → activity_logs → notifications (+recipient rows).
  3. Idempotency & safety: gated by panther.legacy-seed.enabled (default false everywhere), plus a hard skip-with-warning if propertyRepository.count() > 0.
  4. Atomicity: the whole run() method is @Transactional — any failure rolls back the entire import.
✅ EXECUTED. Ran against a fresh Postgres (the project's own docker-compose.yml db service, after clearing unrelated leftover smoke-test data from earlier backend development). PANTHER_SEED_ENABLED=false was used so the bootstrap DataSeeder didn't create its own placeholder admin first.

7. Open Decisions Requiring Confirmation

These records describe real tenants with contradictory data in the source file — only the property manager can give final confirmation. Unlike the first draft of this plan (which defaulted to trusting the room's state), reading both sides of each contradiction directly changed the default: in D1 and D2, the client record carries specific, dated, financially-consistent evidence (exact rent/deposit/rental-type matches, assigned materials with real dates) that a fabricated record would be very unlikely to have by coincidence — the room's status field looks like the side that was simply never updated when the tenant moved in. If either default is wrong, it's a one-row correction after import, not a re-migration.

D1 — client-05 / room-10

client-05's rent (2200), deposit (2200), and rental type (Executive Luxury) all match room-10's real values exactly, plus two dated assigned materials from its claimed move-in date. Only the room number ("VC-12" vs room-10's real "G-401") and property name ("Vision City Executive Villas", which doesn't exist) are stale labels. Default: import client-05 as the current tenant of room-10, setting room-10.status = occupied and current_client_id = client-05. Confirm: is client-05 (Marcus Thorne) actually a current tenant, and is room-10 (Nyarutarama Golf View Lofts, G-401) the correct real room?

D2 — client-04 / room-05

client-04's room number ("A-404"), rent (700), and deposit (700) all match room-05 exactly, plus a dated assigned material. Room-05's own description text ("reserved for incoming diplomatic tenant") is even consistent with a tenant having since moved in. Default: import client-04 as the current tenant of room-05, setting room-05.status = occupied and current_client_id = client-04. Confirm: is client-04 (Claire Uwase) actually a current tenant of room-05?

D3 — exp-06 / "Vision City Executive Villas"

This expense uses the same fictional property name as client-05/pay-06, which both resolve to prop-02 (Nyarutarama Golf View Lofts) via room-10. Expense has no roomId to cross-check directly, so this is a reasoned inference from shared naming, not a hard cross-reference. Default: attribute exp-06 to prop-02. Confirm: was this pool-maintenance expense ($520) actually for a Nyarutarama Golf View Lofts property?
