1. System Overview

Panther PMS is a multi-role property management platform (estates / rooms for rent, East-Africa market). Six roles, five authenticated portals plus one public site.

RolePortal prefixSummary
PUBLIC/Anonymous browsing + booking inquiry + login
CLIENT/client/*Tenant self-service (lease, rent, materials, tickets)
OPERATIONS/operations/*Day-to-day PM: bookings, clients, finance, HR, maintenance
OWNER/owner/*Read-only executive BI / portfolio analytics
HOUSEHOLD/household/*Field staff: checklists, tasks, payslips
ADMIN/admin/*RBAC, property/room/rental-type CRUD, system settings
The frontend currently runs on mock data held in DataContext.tsx. That context's state shape is the data model, and its ~50 mutator functions (addBooking, recordWaterMeterPayment, …) are the required API operations. This plan turns each one into a real REST endpoint backed by a real table.

Each domain package internally follows: controller/, service/, service/impl/, repository/, entity/, dto/, mapper/.

Deviation from the original layout (Phase 7): the activity-log entity and AuditService live in common.audit, not platform as first sketched. Every domain calls AuditService.log(...), but platform.NotificationService depends on iam.User for its broadcast fan-out — keeping AuditService in platform would make iam depend on platform while platform depended back on iam, a circular package dependency. common already sits beneath every domain, so the write path (and its table) moved there; platform keeps the read-only ActivityLogController.

4. Authentication & Authorization

  • Login: POST /api/v1/auth/login with email + password → { accessToken, refreshToken, user }. Access token ~15 min, refresh ~7 days.
  • JWT claims: sub (user id), role, clientId/employeeId (if applicable), name.
  • Every controller method is annotated @PreAuthorize(...) per the matrix below.
  • Row-level scoping: client sees only clientId == principal.clientId records; household sees only own employeeId's tasks/leaves/payroll.
  • Password reset / invite emails: stub an EmailService interface now, wire to a real provider later.
  • public needs no token for /properties, /property/:id, /room/:id, or submitting a booking inquiry (rate-limited).

5. Database Schema

Conventions used everywhere unless noted: every table has id BIGSERIAL PK, created_at, updated_at. Human-facing business numbers (bookingNumber, invoiceNumber, ticketNumber, jobNumber, payrollNumber) become VARCHAR UNIQUE columns generated server-side. Frontend string arrays (amenities, images, rules, photos, certifications) are normalized into child tables rather than JSON columns — the one deliberate improvement over the draft schema already sketched in frontend/README.md.

5.1 IAM domain

users — id, name, email (unique), phone, password_hash, role, avatar_url, title, client_id FK, employee_id FK, status, last_login_at, must_change_password.

system_settings (new — required by Admin System Settings page) — company_name, currency_code, water_rate_per_m3, default_agent_commission_pct, vat_tax_rate_pct, updated_by.

notification_preferences (new — from Profile Settings toggles) — user_id PK/FK, email_notifications, sms_notifications, theme_preference.

5.2 Property domain

properties + property_images, property_amenities. Fields: name, code, location, neighborhood, city, address, description, rating, review_count, featured, year_built, monthly_revenue_estimate, status.

occupiedRooms / availableRooms / reservedRooms / maintenanceRooms / totalRooms are derived from rooms.status grouped by property — a computed read model, not columns to keep manually in sync (avoids the drift risk the current mock data already has).

buildings — property_id FK, name, floors_count, total_rooms (derived).

rental_types + rental_type_included_materials + rental_type_applicable_properties (M:N join). Fields: name (FurnishingType enum), description, price_multiplier, status.

rooms + room_images, room_amenities, room_utilities_included, room_rules. Fields: property_id, building_id, room_number, floor, size_sq_m, bedrooms, bathrooms, furnishing_type, monthly_rent, deposit, status, current_client_id FK, virtual_tour_url, description.

5.3 Leasing / CRM domain

clients + client_materials + client_documents. Fields: name, email, phone, identification_number, nationality, occupation, employer, emergency_contact_*, current_room_id, current_property_id, rental_type, move_in_date, lease_expiry_date, monthly_rent, deposit_paid, payment_status, status, deactivation_reason, notes.

bookings + booking_timeline_events. Fields: booking_number, client_id (nullable — inquiry may precede an account), client_name/email/phone snapshot, property_id, room_id, rental_type_id, requested_date, move_in_date, move_out_date, monthly_rent, deposit, status (9-value enum), notes, source, agent_id.

agents + agent_deals. Referral counters and commission totals maintained by the service layer on each deal write, never client-editable.

5.4 Finance domain

payments — invoice_number, client_id, property_id, room_id, amount, payment_date, due_date, type, method, reference, status, receipt_url, notes.

expenses — property_id, category (9-value enum), description, amount, expense_date, vendor, payment_method, status, receipt_attached, notes.

recurring_bills + bill_payments — name, category, vendor, amount, frequency, next_due_date, status, auto_renew, reminder_days.

payroll_records — payroll_number, employee_id, period, basic_salary, allowances, bonuses, deductions, tax_amount, net_salary, payment_date, payment_status, payment_method.

5.5 Facilities & Maintenance domain

technicians + technician_certifications + tech_documents + tech_work_orders (+ tech_work_order_photos). Work order total_cost = labor_cost + material_cost, derived.

preventive_tasks + preventive_task_photos — property_id, category (15-value enum), task_name, frequency, schedule_week, assigned_staff_id FK → employees, status, remarks, due_date.

damage_reports + damage_report_photos — property_id, room_id, client_id, item, damage_type, description, estimated_cost, amount_charged, responsible_party, status, resolution_notes.

water_meters + water_meter_readings_history — meter_number (unique), previous_reading, current_reading, consumption_m3 (derived), rate_per_m3, total_amount (derived), payment_status.

maintenance_issues + maintenance_issue_photos (tenant-reported tickets, distinct from technician work orders) — ticket_number, client_id, property_id, room_id, category, priority, status, assigned_technician_id.

5.6 HR domain

employees + employee_documents + employee_daily_tasks + employee_damages (+photos) + employee_leaves. Fields: position, department, employment_status, status, basic_salary, national_id, emergency_contact_*.

5.7 Platform domain

activity_logs (append-only audit trail) — occurred_at, user_id, user_name snapshot, role, action, module, details, type. Written by an AuditService from every mutating service method.

notifications + notification_target_roles + notification_recipients. The last table is new — needed for real per-user "read" state, since mock data only has one global read: boolean which doesn't scale past one demo user per role.

Total: 23 primary entity tables + ~20 child/join tables ≈ 43 tables. Full DDL delivered as versioned Flyway migrations during implementation — this section is the field-level spec those migrations are generated from.

8. Cross-Cutting Concerns

  • Business-key generation: central NumberGeneratorService for BK-YYYY-###, INV-YYYY-####, TKT-YYYY-###, WO-#####, PAY-YYYY-MM-### — backed by a Postgres sequence per prefix (the current frontend mock uses Date.now() + Math.random(), unsafe under concurrency).
  • Derived fields: occupancy counts, work-order totalCost, water-meter consumption/totalAmount, agent commission totals — computed server-side on write, never trusted from client input.
  • State-machine side effects (ported from DataContext.tsx, now server-enforced):
    • assignRoomToBooking → booking → room_assigned and room → RESERVED
    • Booking checked_in → room → OCCUPIED, client's current_room_id set
    • Booking completed (move-out) → room → AVAILABLE, client → FORMER
    • addPayment(rent, paid) → client's payment_status = PAID
    • recordWaterMeterPayment → auto-creates a linked payments row (UTILITY)
    • addAgentDeal → increments agent referral/commission totals
    • Employee leave approved / date-crossing → employees.status flips ACTIVE ⇄ ON_LEAVE (nightly scheduled sweep too)
    • Every mutating action writes an activity_logs row
  • File uploads: one shared POST /files/upload used by client/employee/technician documents, damage/issue/preventive-task photos, work-order photos, receipts, bill proofs.
  • Pagination/filtering: Spring Data Pageable + JPA Specifications on every list endpoint.
  • Validation & errors: Bean Validation on DTOs; global @ControllerAdvice → consistent error payload.
  • Notifications (phase 1): DB-stored + polled via GET /notifications/me. WebSocket/SSE push is a phase-2 candidate.
  • Scheduled jobs: bill UPCOMING → OVERDUE sweep, payment PENDING → OVERDUE sweep, leave-status sync, due-date reminder notifications.
  • API versioning: everything under /api/v1; breaking changes get /api/v2.
  • CORS: explicit allow-list of frontend origins, never * once auth is in play.

9. Open Decisions

Confirmed

  1. Database engine: ✅ PostgreSQL.
  2. Build tool: ✅ Maven.
  3. Token transport: ✅ JWT returned in the JSON response body.
  4. File storage for MVP: ✅ Local disk — FileStorageService is an interface, so swapping in S3/MinIO later touches no calling code.

Still open — defaulted for now, revisit before the relevant phase

  1. Payments: defaulted to manual recording only (as today) — affects Phase 4.
  2. Multi-currency: defaulted to the single global toggle already in system_settings — affects Phase 2+.
  3. Denormalized snapshot fields (e.g. propertyName on Room): defaulted to JOIN at read time — affects Phase 2–6.
  4. Email/SMS provider: defaulted to a stub (EmailService + LoggingEmailService) — affects Phase 1 hardening onward.

  • Two real bugs found and fixed while building the suite:
    1. Testcontainers/Spring context-cache interaction bug — every IT subclass inherited the same @DynamicPropertySource method, so Spring's test-context cache reused the first class's (by-then-stale) datasource properties while @Testcontainers/@Container independently stopped/restarted a fresh container per class. Fixed with the standard "singleton container" pattern: start once in a static initializer, never stop explicitly.
    2. Anonymous /auth/me 500'd instead of 401/403 — /api/v1/auth/** was entirely permitAll(), so an anonymous caller's AnonymousAuthenticationToken principal resolved to null for the mismatched @AuthenticationPrincipal UserPrincipal type, and the controller NPE'd. Fixed by narrowing permitAll() to only the genuinely-anonymous endpoints (login/refresh/logout/forgot-password/reset-password), letting /me and /change-password require authentication so Security rejects the request before the controller runs.
